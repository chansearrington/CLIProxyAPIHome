Whole-day usage

Whole-day Management aggregates run in 1.36–4.81 seconds on the verified backup after adding two reporting indexes. The overview remains a separate performance limitation.

The situation

Home's Management usage aggregate can fail after ten seconds when asked for a whole day. Breaking the day into small pieces works but makes reporting slow and awkward. The separate dashboard overview already exceeds the same budget.

This work measured the November 10 verified backup on the Ark, not the live database. The backup contains 3,050,397 usage records. November 8 contains 139,725 records and provides a complete busy-day benchmark. It cannot reproduce November 13 traffic because that traffic is newer than the backup.

Why it is slow

The existing provider-and-time and time indexes find the right rows, but do not hold the fields needed to total them. SQLite repeatedly fetches those fields from a large table that also contains request payloads. The aggregate repeats the work for group counts, metrics and latency percentiles. The overview runs 23 statements and repeats these scans for several rankings.

The limit comes from internal/cluster/management/server.go:84–89, where requestContext gives the request ten seconds. Queueing for a heavy-statistics slot shares that same budget. This change does not raise the limit, increase the connection pool, or move reads onto the writer.

The route is registered at internal/managementhttp/server.go:233; the handler is ListUsageAggregates in internal/cluster/management/usage_observability.go:189. Repository execution starts at internal/cluster/usage_observability.go:765, with metrics and percentile SQL built by the existing shared query functions. The four-connection read-only pool remains separate from SQLite's single writer.

The smallest verified fix

Add two SQLite-only covering indexes in the existing migrateUsageObservabilityIndexes migration. One starts with timestamp; the other starts with the same case-insensitive provider expression as the filter. Both hold the fields required by every aggregate grouping, so SQLite can read reporting values from the index instead of fetching the payload-heavy table rows.

Both retain timestamp DESC, id ordering before the reporting fields. An earlier ascending-order experiment changed floating-point addition by approximately 0.000000000000009; it was rejected. The final definitions preserve complete response hashes and the exact stored bits of aggregate amounts in the tested cases.

Final names are idx_usage_dashboard_time_v1 and idx_usage_dashboard_provider_time_v1. Independent review added the version suffix before first deployment, so a stale pre-review same-name index cannot satisfy this migration accidentally. Measurements used identical column and ordering definitions under the earlier unversioned names; renaming changes no indexed values or scan order.

No handler, response field, filter, group, sorting rule, pagination rule, token expression, percentile rule or PostgreSQL query changes. API documentation is unchanged because the contract is unchanged.

Overview is not fixed

On November 9, Codex overview improves from 26.427 to 10.851 seconds, Claude from 25.233 to 9.968 seconds, and all-provider overview from 42.401 to 17.502 seconds. It still repeats enough work to exceed the unchanged ten-second budget. This PR does not claim otherwise.

Build time and disk space

The exact final definitions took 85.141 and 89.483 seconds to build with Home's Go driver on the 3.05-million-row backup; total migration time was 174.700 seconds. This is a measured maintenance cost, not a safe upper bound for today's larger live database.

The timestamp index occupies 913,195,008 bytes and the provider/timestamp index 951,427,072 bytes: 1,864,622,080 bytes total, approximately 1.74 GiB of permanent space on this backup. This also adds ongoing index-maintenance work when usage rows are written. A second exact-definition build sampled open sort files every 20 ms. Peak sort-file size was 932,003,351 bytes (about 889 MiB), with a peak rollback journal of 949,528 bytes. That instrumented repeat took 118.818 and 120.562 seconds, 239.482 seconds total, illustrating real timing variation. The same migration with both indexes already present took 1.945 ms. Reserve substantially more than the measured roughly 0.87 GiB temporary peak, plus 1.74 GiB permanent growth, for a larger live database; these measurements are not a production-space cap.

Smaller alternatives: a billing-only covering index took 14.871 seconds plus 0.961 seconds to analyze, but did not remove usage-table fetches; a diagnostic sum improved only from 3.949 to 3.083 seconds. It was rejected. Two materially narrower usage indexes (identity and latency fields, without token totals) took 85.305 and 89.355 seconds to build, essentially the same build time, yet whole-day all-provider credential aggregation still took 9.227 seconds versus 4.670 seconds with the selected indexes. Codex/model took 4.495 versus 2.024 seconds. The narrower pair saved approximately 369 MiB of permanent index space but did not provide a shorter maintenance window or enough margin under the request budget. It was rejected.

Required deployment sequence

Do not ship as an ordinary restart

Missing indexes would be built at Home start and hold startup for several minutes. Building them on a running SQLite database also holds the database write lock and can interrupt ingestion and liveness writes. Operator locks coordinate maintenance; they do not remove this database lock.

  1. Use a separately approved and announced overnight maintenance window, with independent direct recovery positively tested, all four fleet locks and fleet policy paused. The measured 175-second build is a floor for planning, not the total maintenance-window length. Today's larger database and competing disk activity can take longer.
  2. Check free array and temporary-file space first. Preserve both SQLite temporary-directory settings and place sort files on the data volume, not the small container temporary filesystem. Account for the permanent index sizes and temporary/journal reserve below.
  3. Before the image swap, pre-build the two indexes on the current database using exactly this commit's names and definitions. Treat the build as a disruptive maintenance operation. Do not improvise a live command from this report.
  4. Read sqlite_master and PRAGMA index_xinfo and verify both complete definitions against a freshly migrated isolated database at this commit. Names alone are insufficient: IF NOT EXISTS does not check that an existing same-name index has the right columns or order. Recheck query plans and a whole-day response.
  5. Only after the definitions are verified, swap the reviewed image. The migration's IF NOT EXISTS statements then do no rebuilding. Complete normal fleet acceptance before restoring policy and releasing locks. Keep independent recovery available throughout.

No deployment or production index creation is part of ws-0051. The code-only PR must not be merged or deployed by this helper.
