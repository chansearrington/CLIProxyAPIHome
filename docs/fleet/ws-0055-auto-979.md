# Decision 979 automatic ordering — operator runbook

Python 3.9 standard library only. Source: `scripts/fleet/auto979/`. No Go or Home changes.
The installer is **shadow only**, not permission to enable live priority updates.

## Contract and ordering

- GET `/v8/management/credentials` returns `files`; use UUID, email, integer priority,
  `disabled`, and `reauth_required`. GET `/v8/management/quota/credentials/:id` supplies
  full quota windows. The list equivalent is `/v8/management/quota/credentials`.
- Weekly means exactly `claude-seven-day`: unlabeled account scope, week × 1,
  percentage unit, limit 100. `used=1` means **1% used**, not exhausted.
  `reset_at` is its renewal, not `earliest_reset_at` (which may mean the five-hour window).
  See `internal/quota/providers.go`, `internal/managementhttp/routes_v8.go`, and
  `docs/management/api.md` for the authoritative implementation and contract.
- Eligible accounts with room go first by weekly renewal, then 100%-used accounts by
  their renewals. Reserve is always last among eligible accounts. Disabled/reauth-required
  accounts retain their exact priority; only the other occupied slots are reassigned.
  The configured disabled fallback at priority 1 is validated and **never PATCHed**.
- Within each room/exhausted group, renewals at most 120 seconds apart preserve the
  live relative order. Contradictory pairwise tie chains fail closed rather than churn.
- Holdouts are UUID + timezone-aware `until` entries in `979.json`; while unexpired,
  they follow the ordinary accounts, just before the reserve. Multiple holdouts keep
  their live relative order. Disabled/reauth holdouts remain untouched.
- Revised stale-data rule: a saved future weekly reset remains usable; the saved used
  percentage determines its group and is logged as an assumption when stale. A passed
  reset assumes room but an unknown next reset: after known-reset room accounts,
  preserving its previous relative position, before exhausted accounts. No quota fetches.
  Missing reset, invalid percentage, ambiguous weekly windows, or changed inventory fail closed.
- The state-change cap is **N=3** by default (`max_state_changes`). More than N unexpected
  eligibility/exhaustion/reset changes block the run without replacing the baseline.
  A rollover after the saved reset is expected. Review before changing this threshold.

## Safety and files

`--dry-run` (also the default) prints live/computed priorities and quota evidence with
six-character labels/IDs; it writes nothing. `--shadow` makes only GETs, but records the
private log and baseline. `--apply` needs an existing shadow baseline and patches only
changed priorities, using only `{"id":...,"priority":...}` at the v8 fields endpoint.

Before writes: re-read credential state, verify plan/holdout timing, save and verify
`/mnt/cache/appdata/cpa-home/data/backups/home-config-*.json`, retaining only the newest two.
This uses the existing `taken_utc`/`purpose`/`accounts[].attributes.priority` JSON shape,
but is intentionally **priority-only**, not the old broad settings/token-fingerprint snapshot.
Its rollback scope is only those priorities; never restore auth JSON or a whole database.

The durable `979-STOP.json` latch is saved before the first PATCH. Any failed or uncertain
write/readback leaves it in place; later schedules do no writes. Successful independent
GET/readback, baseline save, and JSONL append precede latch removal. There are no write
retries or automatic rollback. Home 1.1.9 has no multi-account transaction: a brief or
failed partly applied order is possible. The lead reconciles it; all enable/sign-in
settings and credentials remain untouched. Never remove STOP without inspecting Home.

Log: `/mnt/cache/appdata/cpa-home/fleet-jobs/979-apply.jsonl`, root-owned **0600**;
containing directory **0700**. Every scheduled result records UTC time, mode and reason.
Computed-order records include full ordered priorities, six-character labels and full
addresses for Operations to compare, quota assumptions, backup name, and readback result
(`null` means not attempted). No token, password, arbitrary API errors, or credential JSON.

## Lead-run setup (not run by the helper)

Copy `scripts/fleet/auto979/` to a fresh Ark staging directory, for example `/tmp/auto979-stage/`.
Run the following **on the Ark as root**. Do not turn on live applies in this setup.

```sh
umask 077
mkdir -p /mnt/cache/appdata/cpa-home/fleet-jobs
chmod 700 /mnt/cache/appdata/cpa-home/fleet-jobs
set +x; set -a; . /mnt/cache/appdata/cpa-home/.env; set +a
python3 -I /tmp/auto979-stage/prepare.py --legacy /mnt/cache/appdata/cpa-home-build/ws0048-2d5fbf1/apply979.py --migrated-output /tmp/apply979-v8.py --config-output /mnt/cache/appdata/cpa-home/fleet-jobs/979.json
python3 -I /tmp/apply979-v8.py --dry-run
python3 -I /tmp/auto979-stage/auto979.py --config /mnt/cache/appdata/cpa-home/fleet-jobs/979.json --dry-run
```

`prepare.py` reads TARGET as a literal (never executes the old script). It joins the
existing 12 addresses to v8 UUIDs and uses the last TARGET entry as reserve. Verify that
entry is the approved reserve before proceeding. The remaining disabled priority-1 UUID
is fallback. Existing outputs are refused, so configuration/holdouts cannot be silently reset.
Compare the dry-run against the Nov 18 09:43Z list. For each difference inspect logged
weekly used/reset/observation and stale/passed-reset assumptions; do not call an old list
current evidence. Live API compatibility and this comparison are lead acceptance checks.

After the migrated script's dry-run, install it over the old `apply979.py` with `install -m 700`
(the only source change is `/v0/management/auth-files` → `/v8/management/credentials`).
The old TARGET, targeted-backup caller, fields PATCH, and default dry-run behavior remain.
Then install/run the shadow job.

```sh
python3 -I /tmp/auto979-stage/install-shadow.py
/bin/bash /mnt/cache/appdata/cpa-home/fleet-jobs/auto979/run-shadow.sh
stat -c '%U %a %n' /mnt/cache/appdata/cpa-home/fleet-jobs/979-apply.jsonl
```

Installer matches the Ark's existing **User Scripts** plugin: preserves other entries in
`/boot/config/plugins/user.scripts/schedule.json`, adds `cpa-auto979-shadow` with custom
`*/5 * * * *`, mirrors runtime schedule, regenerates the plugin's custom cron file and
calls `update_cron`. Both script and schedule survive reboot. It never restarts Home or
nodes. Verify `crontab -l` and a later timestamped log entry; reboot survival is not proven
until an actual reboot. Disable/delete only this job through User Scripts to stop it.
