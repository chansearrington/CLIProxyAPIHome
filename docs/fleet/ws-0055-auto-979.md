# Decision 979 automatic ordering — operator runbook

Python 3.9 standard library only. Source: `scripts/fleet/auto979/`. No Go or Home changes.
The installer is **shadow only**, not permission to enable live priority updates.

## Contract and ordering

- GET `/v8/management/credentials` returns `files`: use UUID, email, integer priority,
  `disabled`, and `reauth_required`. GET `/v8/management/quota/credentials/:id` supplies
  full quota windows. The list equivalent is `/v8/management/quota/credentials`.
- Weekly means `claude-seven-day`: unlabeled account scope, week × 1, percentage unit,
  limit 100. `used=1` means **1% used**, not exhausted. Use its `reset_at`, never the
  five-hour/other-window `earliest_reset_at`. Authoritative sources are
  `internal/quota/providers.go`, `internal/managementhttp/routes_v8.go` and the API docs.
- Room-left accounts go first by weekly renewal, then 100%-used accounts by their
  renewals. Reserve is last among eligible accounts. Disabled/reauth-required accounts
  keep their exact priority slots; only remaining slots are reassigned. Fallback must
  remain priority 1 and is **never PATCHed**, whether enabled or disabled.
  Shared count comes from the configured UUID list (currently 12), not a fixed constant.
- Renewals within 120 seconds keep live relative order within each room/exhausted
  group. A contradictory tie cycle keeps its members in live order, logs
  `tie_cycle_kept_live_order`, and sorts the remaining accounts normally.
- Holdouts are UUID + timezone-aware `until` entries in `979.json`. Until expiry they
  follow ordinary accounts, just above reserve; multiple holdouts keep live order.
  Quota is not fetched/required for reserve or active holdouts. Disabled/reauth holdouts
  stay untouched.
- Stale future resets remain usable; saved percentage determines the group with a
  logged assumption. Passed resets assume room and unknown next renewal: after known
  room-left renewals, preserving live relative order, before exhausted accounts.
  A null/missing reset falls back to saved state. A reset never seen in either source
  freezes that account's slot and logs an exclusion; **more than two** such accounts
  blocks the run. No quota fetch/refresh operation is triggered.
- Default cap **N=3** (`max_state_changes`) blocks unexpected eligibility/exhaustion/reset
  changes inside a short interval. Reset noise up to 120 seconds is ignored; expected
  rollovers are exempt. A baseline older than two hours is replaced from current
  observations with `rebaseline_after_gap`, avoiding permanent blockage after an outage.
  Invalid amounts, ambiguous weekly windows or changed inventory still fail closed.

## Safety and evidence

`--dry-run` (the default) prints live/computed order, weekly evidence and exclusions;
it writes nothing. `--shadow` makes only GETs, saving private state and selected log
entries. `--apply` requires an existing shadow baseline and PATCHes only changed
priorities, with only `{"id":...,"priority":...}` at the v8 fields endpoint.

Before writes: independently re-read credentials, check plan/holdout timing, and verify
`/mnt/cache/appdata/cpa-home/data/backups/auto979-config-*.json`. Keep the newest **two
of that prefix only**; never delete/prune `home-config-*`. Backups use the existing
`taken_utc`/`purpose`/`accounts[].attributes.priority` shape, but only priorities, UUIDs,
six-character labels/IDs and disabled flags. They contain no full addresses or tokens.
Rollback restores only priorities, never auth JSON or a whole database.

The durable `979-STOP.json` latch is saved before the first PATCH. Failed/uncertain
writes or readback leave it in place, forbidding later writes. Successful independent
readback, state save and apply log precede latch removal and a STOP-cleared log entry.
No write retries or automatic rollback. Home 1.1.9 has no multi-account transaction:
a briefly mixed or failed partly applied order is possible. The lead reconciles it;
credentials and enable/sign-in settings remain untouched. Never remove STOP blindly.
The migrated manual script takes the same `979.lock` and refuses STOP, including dry-run.

Log `/mnt/cache/appdata/cpa-home/fleet-jobs/979-apply.jsonl`: root-owned **0600**, directory
**0700**. Lines are limited to applies, errors, state/order changes and an hourly
heartbeat. Latched STOP logs at most hourly. Entries have UTC time/reason/mode, full
ordered priority numbers, six-character labels plus id6, assumptions/exclusions, backup
name and readback result (`null` = not attempted). **No full email addresses** in log,
STOP, saved state or backup labels. Operations compares labels with the lead's ordered
account list. Never log arbitrary API errors, tokens, passwords or credential JSON.

## Apply mode (2026-11-19)

Shadow matched both hand-applied renewals on 11-19 (03:38Z and 13:05Z, Hype ask 118793). The Hype
Orchestrator approved apply mode on three conditions: the save fix is proven (ws-0048 isolated-clone
PATCH proof, live since 11-13), a different model reviewed the apply path, and the job cannot write
during an upgrade or rollback.

**What apply writes, and when.** Only Claude `priority` values, and only when a weekly renewal changed
the *computed* order since the last run (the state file keeps the last computed order). If someone
changes live priorities by hand, the job keeps that edit (`live_differs_no_new_renewal_kept`, logged
once) until the next renewal recomputes the order. A state file from before this change has no saved
computed order, so the first runs never write. Before every single PATCH it re-reads the live
priorities; any change it did not make stops the pass with the STOP latch. Residual: a panel edit
landing in the milliseconds between that read and the PATCH can still be overwritten (Home has no
conditional priority update); the final read-back then fails and latches STOP.

**Hold: the maintenance and emergency stop.** Always create the hold *under the job lock*, so a pass
in flight finishes first and every later pass refuses before any read or write (`operator_hold_no_writes`):

```sh
flock /mnt/cache/appdata/cpa-home/fleet-jobs/979.lock touch /mnt/cache/appdata/cpa-home/fleet-jobs/979-HOLD
```

Release with `rm /mnt/cache/appdata/cpa-home/fleet-jobs/979-HOLD`. Every Home/node maintenance window
takes the hold before pausing the fleet policy and releases it after acceptance. Never create or edit
`979-STOP.json` by hand: it is the job's own write latch. As a second line, `--apply` also refuses
(`fleet_maintenance_paused_no_writes`) unless `GET /fleet` shows `policy.enabled` true right before
the backup.

**Switch to apply.** Take the hold. Install the reviewed `auto979.py` and `run-apply.sh` into
`/mnt/cache/appdata/cpa-home/fleet-jobs/auto979/` (root, 0700) and check their SHA-256 against the
merged commit. Point the one line in `/boot/config/plugins/dynamix/auto979.cron` at `run-apply.sh`,
run `update_cron`, check `crontab -c /etc/cron.d -l`, then release the hold. Back to shadow: the
same steps with `run-shadow.sh`.
