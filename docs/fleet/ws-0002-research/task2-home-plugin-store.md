Ref read: `upstream/dev` = **04fac5f** (router-for-me/CLIProxyAPIHome, release 1.0.73), extracted with `git archive` to `/tmp/ws-0002-research/home-dev`. All paths below are repo-relative "at upstream/dev 04fac5f" unless prefixed **SDK:** which means the pinned CPA module Home compiles against, `github.com/router-for-me/CLIProxyAPI/v7 v7.2.83` (go.mod:11), read from the local module cache. No files were modified, nothing built, no server touched.

**One-paragraph summary.** Home's "plugin store" is a *catalogue + config writer*, not an artifact host. `GET /plugin-store` fetches one or more `registry.json` files over HTTPS (the official GitHub-hosted one is always included; extra ones come from the existing config key `plugins.store-sources`). `POST /plugin-store/:id/install` resolves a pinned manifest (GitHub release tag, or direct artifact URLs+SHA-256) and writes it into the DB-backed config at `plugins.configs.<id>.store` — it downloads nothing. Every CPA node, on every config push (and at startup), asks Home `GET plugin-sync` over mTLS RESP; Home answers with one artifact **URL + SHA-256** (+ optional download credentials) per plugin for that node's OS/arch, and the **node downloads and verifies** the artifact itself. Home only downloads/loads a plugin into its own process when `plugins.configs.<id>.load-in-home: true`, and that is a hard requirement for two things the fleet needs: OAuth login through the plugin, and the plugin's credentials being dispatchable at all. `/plugin-store-auth` is NOT provider login — it is credentials for fetching registries/artifacts. Provider login is `GET /v0/management/<provider>-auth-url` + `/get-auth-status` polling, which is a generic start/poll contract that a device-code flow fits. Successful logins land in the same `auth` table and dispatch path as native credentials. Pooling by model name across providers is inherent in Home's dispatcher (selection happens in Home), but the quota-snapshot view has a hard-coded provider allowlist that excludes any plugin provider. Home never checks CPA node version or plugin ABI; the node does that at load time.

## Q1. Where does the catalogue come from; what do list/install do; where does the artifact end up

### Catalogue source
- The list of registries is built by `pluginStoreSources(cfg)` → `pluginstore.NormalizeSources(cfg.Plugins.StoreSources)` — `internal/cluster/management/plugin_store.go:470-475`.
- **SDK:** `NormalizeSources` always seeds the result with `DefaultSource()` first and then appends each configured URL, de-duplicated by URL and by derived ID — `internal/pluginstore/registry.go:86-111`. The built-in source is hard-coded: `DefaultRegistryURL = "https://raw.githubusercontent.com/router-for-me/CLIProxyAPI-Plugins-Store/main/registry.json"`, ID `official`, name `Official` — `registry.go:15-17, 78-84`. Extra sources get ID `source-<first 12 hex of sha256(url)>` and name = URL host — `registry.go:113-124`.
- The config field already exists: `PluginsConfig.StoreSources []string yaml:"store-sources"` with comment "appends third-party plugin store registries to the built-in official source" — `internal/config/plugin_config.go:17-18`; normalised (trimmed, blanks dropped) at `plugin_config.go:114-124`; documented in `config.example.yaml:126-128`.
- So it is **neither hard-coded-only nor a single remote index**: it is the official index **plus any operator-supplied registry URLs**. An operator can point Home at a registry they host themselves.

### Can an operator register an arbitrary third-party plugin? Smallest change
**Yes, with zero Go changes.** Three working routes, in order of preference:
1. **Self-hosted registry (recommended).** Host a `registry.json` (`schema_version: 2`) on any HTTPS static host, with one `direct` entry whose `install.artifacts[]` lists `{goos, goarch, url, sha256, size}` for `linux/amd64` (Ark), `darwin/arm64` (minis) etc. Add its URL to `plugins.store-sources` (via `PUT /config.yaml` — `management/config.go:69-110`). Then `GET /plugin-store` lists it (under a `source-…` ID) and `POST /plugin-store/<id>/install` pins it. Artifacts can live anywhere HTTPS (GitHub release assets work as plain URLs, no `api.github.com` involvement for `direct`). If the artifact host needs auth, add a `/plugin-store-auth` rule (Q3). Size: config only; ~0 LOC. Also requires `plugins.enabled: true` globally (`plugin_sync_plan.go:48`; node side `sync.go:123`).
2. **GitHub-release registry entry.** Same self-hosted `registry.json` but `install.type: github-release` + `repository: https://github.com/<owner>/<repo>`; the repo's releases must publish `<id>_<version>_<goos>_<goarch>.zip` and `checksums.txt` (`plugin_sync_plan.go:166-170, 197-215`). Home then needs outbound access to `api.github.com` at install and at every plugin-sync build (unauthenticated GitHub API is rate-limited; a `github-token` store-auth rule fixes that).
3. **Hand-written manifest, no registry at all.** `PUT /config.yaml` with `plugins.configs.<id>: {enabled: true, store: {id, version, schema-version: 2, install: {type: direct, artifacts: [...]}}}` — `PutConfigYAML` accepts the raw YAML root and only validates it (`config.go:76-86`); `storeManifestFromPluginConfig` validates the manifest (`plugin_sync.go:629-648`; **SDK** `manifest.go:102-148`). This bypasses the store UI but is the least code and needs no hosting of a registry. Caveat: `/plugin-store` will then show it only if some registry also lists that id.
If you wanted the store to show a plugin **without** hosting a registry file, the smallest code change would be a new config list (e.g. `plugins.extra-entries: []pluginstore.Plugin`) merged into `fetchSourcedPlugins` at `plugin_store.go:507-509` — roughly 30–50 LOC + tests. Not recommended; route 1 is already supported upstream.

### Docs vs code (Q1)
- `docs/management/api.md:897` says for direct installs "Home-mode CPA nodes resolve the current-platform artifact URL and SHA-256 **from that registry** during runtime config application". **Code disagrees**: install pins the registry entry's artifact list into config (`plugin_store.go:596-618`) and `plugin-sync` selects from that pinned `manifest.Install` (`plugin_sync_plan.go:128`) — neither Home nor the node re-reads the registry on the sync path (nodes only fall back to the registry when Home reports plugin-sync unsupported, **SDK** `home_plugins.go:53-57`). Consequence: after install, changing artifacts in your registry does nothing until you re-install/bump the version.
- `api.md:847/897` document `load-in-home: true`; code also accepts `home: true` and `home: {enabled: true}` / `home: {load: true}` (`plugin_runtime.go:339-351`) — undocumented aliases, not a contradiction.
- `api.md` example for `/plugin-store` shows `"registered": false`; code never sets that field in this route (`plugin_store.go:196-220`), so it is always `false` — harmless but misleading.

## Q2. Manifest format, version/ABI checks, how nodes learn what to install

### Schema versions in play (three different numbers)
| Thing | Constant | Where enforced |
| --- | --- | --- |
| Registry file `schema_version` | 1 or 2 (`direct` needs 2) | **SDK** `internal/pluginstore/registry.go:18-19, 167-174` |
| Stored manifest `schema-version` | 0 (absent) or 2 for `direct`; unused for `github-release` | **SDK** `manifest.go:10, 112-114`; Home writes it only when non-zero `plugin_store.go:557-559` |
| Plugin-sync wire protocol `schema_version` | `PluginSyncSchemaVersion = 1` | **SDK** `home_sync.go:10`; Home rejects others `plugin_sync_plan.go:32-34`; node rejects others `home_sync.go:51-53` |

### Manifest Home stores and ships (`plugins.configs.<id>.store`)
**SDK** `manifest.go:9-26`: `schema-version, id, name, description, author, version, release-tag, repository, logo, homepage, license, tags, source-id, source-name, source-url, install{type, artifacts[]}`. `Manifest.Validate()` — `:102-148`: `version` required and must match `^[0-9][0-9A-Za-z.+-]*$` (leading `v` stripped); `direct` → valid id, and either a validated pinned artifact list (`https`-only, no userinfo/query/fragment — `:150-164`) or a valid `source-url`; `github-release` → `release-tag` required and must resolve to the same version. For the **plugin-sync response** a direct item must have pinned artifacts and all `https` (`home_sync.go:83-98`).

Home-owned keys next to `store` in `plugins.configs.<id>`: `enabled` (nil → false), `priority` (`internal/config/plugin_config.go:24-31, 33-76`), `load-in-home` / `home` (`plugin_runtime.go:339-351`). Every other key is preserved verbatim as the plugin's own config (`Raw yaml.Node`, `plugin_config.go:29-30, 78-103`) and passed to a Home-loaded plugin via `pluginInstanceConfigs` (`plugin_runtime.go:307-326`).

Node-side plugin-sync request: `PluginSyncRequest{schema_version, goos, goarch, installed_versions map[id]version}` (**SDK** `home_sync.go:12-17`). Response: `{schema_version, expires_at, items[{manifest, auth[]}]}` (`:27-45`). No other fields.

### Does Home check the CPA node version or plugin ABI? **No.**
- Searched `internal/home`, `internal/cluster`, `internal/respserver`, `internal/node` for `abi`, `ABIVersion`, `CPAVersion`, node version gating: **not found**. The only "protocol version" is the RESP membership protocol (`internal/cluster/membership.go:100`, `respserver/server.go:488`), unrelated to plugins.
- The plugin-sync request carries only goos/goarch/installed versions (above), so Home cannot tell what CPA version or plugin ABI a node runs.
- The ABI check is done **on the node at load time**: **SDK** `internal/pluginhost/loader_unix.go:154-156` rejects a plugin whose `abi_version != pluginHostABIVersion`; `sdk/pluginabi/types.go:6-10` declares `ABIVersion uint32 = 1` and says new capabilities are gated by flags/method names, not by bumping the version. Home only learns about a load failure indirectly from the node's `plugin-status` report (`node/plugin_status.go:46-57` `load_status`, `error`), surfaced in `/nodes` as `plugin_report_state` (docs `api.md:674`). **Home itself does the same ABI check when it loads a `load-in-home` plugin**, because it uses the same SDK host (`newPluginHostForRuntime` → `sdkpluginhost.New()` `plugin_runtime.go:19-22`).

### How a node learns which plugins to install — push, not poll, not a separate subscription
1. Install/uninstall/config edit → `refreshConfig` → `runtime.PublishConfigYAML` (`management/server.go:96-110`, `internal/home/config_yaml.go:91-…`) fans the sanitised config YAML out to every node's existing **config subscription** (`internal/respserver/subscribe/`). The `plugins:` section rides inside that YAML.
2. **SDK** node: `StartConfigSubscriber` callback → `applyHomeOverlayContext` (`sdk/cliproxy/service.go:1595-1601, 1432`) → `syncHomePlugins` (`:1458`, `home_plugins.go:24-63`): if the `plugins:` section hash changed (`:143-170`) it sends `GET plugin-sync` (`internal/home/client.go:938-980`), installs the returned items (`homeplugins.SyncResolvedWithReport`), loads them (`MarkLoadResults` `service.go:1463-1468`), reports `RPUSH plugin-status` (`home_plugins.go:100-113`), then `GET plugin-tasks` for pending deletes (`:115-137`). Also once at startup (`cmd/server/main.go:311-345`).
3. **What Home ships is a URL, never bytes.** The `plugin-sync` reply contains, per plugin, one `{goos, goarch, url, sha256}` artifact plus optional HTTP credentials for that URL (`plugin_sync_plan.go:135-137, 191-194`; wire encoding `get/plugin_sync_json.go:48-97`). The node performs the download and SHA-256 verification (**SDK** `homeplugins/sync.go:346-364`; `pluginstore/direct.go:46-50`). The reply is valid for 10 minutes (`plugin_sync_plan.go:22`).
4. There is no periodic re-check on Home's side; if a node missed the push it catches up on its next config subscription delivery or restart.

## Q3. `/plugin-store-auth`, plugin OAuth/login flows, where credentials go, how the scheduler sees them

### `/plugin-store-auth` is NOT provider login — it is download credentials
Routes `internal/managementhttp/server.go:172-176` → handlers `internal/cluster/management/plugin_store_auth.go:144-228`. A rule is `{name, match (absolute https prefix), apply_to [registry|metadata|artifact], auth_type none|bearer|basic|header|github-token, token/username/password/header_name/header_value, enabled}` (`:98-109`; validation `internal/pluginauth/service.go:473-511`). Secrets are AES-sealed with a per-database key (`internal/cluster/plugin_store_auth.go:26-55`, table `plugin_store_auth_key`; records in `plugin_store_auth` `cluster/models.go:298-323`), write-only in responses (`service.go:610-617`), first-match-wins (docs `api.md:1042`). They are used when Home fetches registries/releases (`plugin_store.go:158-163, 245-250`) and when Home builds plugin-sync plans (`plugin_sync_plan.go:102-106`), and **they are forwarded to nodes inside the plugin-sync reply** so the node can download a private artifact (`plugin_sync_plan.go:136, 194`; `plugin_sync_json.go:75-97` base64-encodes `token/username/password/header_value`). So a store-auth token does leave Home — to every node, over mTLS. Docs `api.md:1040-1075` match the code.

### Provider login for a plugin — `GET /v0/management/<provider>-auth-url`
- There is no static route. Unknown `/v0/management/*` GETs fall into `clusterManagementNoRoute` (`managementhttp/server.go:730-771`): it sets build headers, runs the SDK management-key middleware (`:757-765`), then calls `clusterHandler.ServePluginAuthURL(c)` (`:766`).
- `ServePluginAuthURL` — `internal/cluster/management/plugin_oauth.go:146-190`: derives `<provider>` from the path (`pluginAuthProviderFromManagementPath` `:299-308`, lowercase `[a-z0-9-]`), and returns `false` (→ 404) unless **`runtime.HasPluginAuthProvider(provider)`** — which is `pluginHost.HasAuthProvider` (`internal/home/plugin_runtime.go:99-101`). **Therefore the plugin must be loaded inside the Home process** (`load-in-home: true`, Home built with CGO, an artifact for Home's GOOS/GOARCH — linux/amd64 in the Ark container). A plugin that only lives on the nodes cannot be logged in through Home.
- Flow: callback base URL = `<scheme>://<host>/v0/management/oauth-callback` from `X-Forwarded-Proto/Host` or the request host (`:156, 310-355`) → `runtime.StartPluginLogin(ctx, provider, baseURL)` → `pluginHost.StartLogin` (`plugin_runtime.go:104-112`) → plugin returns `{URL, State, Metadata}` → state validated (`:171-176`) → an `oauth_sessions` row is written with `data.source="plugin"` plus the plugin's metadata (`:182, 255-267`; `registerOAuthSession` `oauth_login.go:626-635`) → response **`{"status":"ok","url":..., "state":...}`** (`:188`).
- The panel then polls `GET /get-auth-status?state=` (`server.go:377`; `oauth_login.go:320-365`) → for plugin sessions `respondPluginAuthStatus` (`plugin_oauth.go:192-253`) → `runtime.PollPluginLogin(provider, state, metadata)` (`plugin_runtime.go:115-123`) → plugin returns `pending | error | success`. On `success`, `PluginLoginAuths` decodes one or many `AuthData` (`plugin_runtime.go:126-163`; multi-account in one login is supported via `resp.Auths`, `:149-152`).
- Redirect-based OAuth: `POST /oauth-callback` (`server.go:380`, `oauth.go:294-296`, `handleOAuthCallback` `oauth_login.go:367-…`) stores `callback_code`/`callback_provider` into the session data (`pluginOAuthCallbackSessionData` `plugin_oauth.go:455-464`), and that data (minus `source`) is what the next poll hands to the plugin (`pluginOAuthPollMetadata` `:273-280`, used at `:202`). (I read the helper and the poll wiring; the exact branch inside `handleOAuthCallback` that invokes `pluginOAuthCallbackSessionData` — around `oauth_login.go:420-499` — was not read line-by-line.)
- **Device-code flow:** the plugin contract is generic *start → (url, state) → poll until success*, with the plugin free to do the device-code polling inside `PollLogin`. Nothing in Home requires a redirect. Home's own native kimi and meta logins are device-code flows on exactly this start/poll shape (`oauth_login.go:146-183, 276-318`) and return `user_code` alongside the URL (`:295-316`). **Gap:** for plugin providers `ServePluginAuthURL` returns only `url` and `state` (`:188`); the plugin's `Metadata` (where a `user_code` would live) is persisted in the session but **not returned to the panel**. So a device-code plugin works if it returns a `verification_uri_complete`-style URL that already embeds the code; if it needs the user to type a code, the code is not surfaced by Home today (a ~5-line change at `plugin_oauth.go:188` to echo `resp.Metadata["user_code"]`).

### Where the resulting credential goes — Home's DB, same table, same dispatch path
- On `success`: `runtime.PluginLoginAuths` → `pluginHost.AuthDataToCoreAuth(authData, "", "")` (`plugin_runtime.go:155`) → **SDK** `internal/pluginhost/auth_provider.go:537-589`: `Provider = data.Provider`, **`ID = data.ID`** (or derived from file name if empty, `:563-566`), `Label`, `Prefix`, `Storage = pluginTokenStorage{rawJSON: data.StorageJSON}`, `Metadata` (+`type=<provider>`), `Attributes`, `NextRefreshAfter`. Converted to Home's auth type by `pluginAuthToHomeAuth` (`plugin_runtime.go:412-440`; the raw storage JSON is flattened into `Metadata` `:460-485`).
- Then **`h.repo.UpsertAuth(ctx, auth, "upsert")`** for each auth (`plugin_oauth.go:229-236`) → the same `auth` table every native credential uses (`internal/cluster/models.go:91-121`; `repository.go:157-173`), then `refreshAuths` → `runtime.ReloadAuths` (`:237-242`, `management/server.go:124-130`) and the OAuth session is completed (`:243-247`). **Not node-local.** It is subsequently dispatched to nodes exactly like a native credential (Q3 last bullet).
- **Multiple accounts:** each successful login upserts by `auth.ID`. If the plugin returns a distinct `AuthData.ID` per account ("stable host auth identifier", **SDK** `sdk/pluginapi/types.go:214-215`), you get separate rows/credentials; if it returns the same ID, the second login **overwrites** the first. Identification = `ID`, `Index` (`EnsureIndex`), `Label`, `FileName`, `Attributes` — all chosen by the plugin. Whether the community Copilot plugin derives the ID from the GitHub login/account is a Task 1 question.

### How a plugin-provider credential looks to the scheduler vs a native one
- **Same table, same in-memory manager, same candidate loop.** `Dispatch` iterates every auth in `m.auths` (`internal/cliproxy/auth/manager.go:1400-1445`), filtering on `Disabled`, retry round, exclusions, `provider ∈ providers` (`providers` = every distinct `auth.Provider` with an enabled auth — `internal/home/auth_apply.go:186-210`, called at `runtime.go:947`), and **`registry.ClientSupportsModel(candidate.ID, routeKey)`** (`:1441`). No provider allowlist.
- **Model registration is the one place a plugin credential differs**, and it is a hard dependency: `registerModelsForAuth` (`internal/home/models.go:171-…`) first calls `tryRegisterPluginModelsForAuth` (`:214`; `plugin_runtime.go:165-248`) → `pluginHost.ModelsForAuth`. If a Home-loaded plugin owns the provider it returns `Handled=true` and the models are registered under that provider (`:238-244`). If **no plugin is loaded in Home for that provider**, `Handled=false`, control falls to the provider `switch` whose `default` branch (`models.go:335-453`) finds no config models, `appendPluginModels` adds nothing (`:444`, `plugin_runtime.go:250-289`), and the credential is **unregistered from the model registry** (`:453`) → `ClientSupportsModel` is false for every model → **never dispatched**. Conclusion: for the fleet, `load-in-home: true` is mandatory for Copilot credentials to route, independent of the OAuth question.
- Refresh: `Manager` calls `refreshViaPlugin` first (`internal/cliproxy/auth/plugin_hooks.go:45-56`; `manager.go:2668-2670, 2785-2787`) → `runtime.RefreshAuth` → `pluginHost.RefreshAuth` (`plugin_runtime.go:64-80`). Again requires the plugin in Home.
- Disabled / exhausted / cooldown handling is provider-agnostic (Q4).
- Dispatch to the node: `POP` dispatch reply carries `provider`, `model`, `auth_index`, and the full sanitised auth JSON (`internal/respserver/pop/dynamic/dispatch.go:128-202`; `SanitizeAuthForDownstream` `internal/home/auth_sanitize.go:11-41` strips `refresh_token`/`service_account`). The **node** must have the same plugin loaded to execute a request for that provider — node-side behaviour is Task 3.
- Optional: a plugin can also act as **scheduler** (`PickAuth`, `plugin_hooks.go:230-264`, `manager.go:1454-1461`) — not needed here.

## Q4. Usage / quota for a plugin provider

### Usage push → per-credential stats: works, provider-agnostic
- Node pushes `LPUSH usage <json>` (`internal/respserver/push/register.go:10-14`) → `handleUsage` (`push/usage.go:32-79`): validates JSON, strips provider API-key secrets (`cluster.SanitizeUsagePayloadSecrets` `cluster/usage.go:247-285` — only touches `auth_type == provider_api_key`), stamps the reporting CPA identity, then **always** `Runtime.RecordUsagePayload` (`:60`) and `PersistClusterUsagePayload` (`:61`).
- `RecordUsagePayload` — `internal/home/usage_result.go:12-46`: reads `auth_index`, `provider`, `model`, `fail.status_code`/`failed`/`fail.body`, builds `coreauth.NewUsageResult` and calls `coreManager.MarkResult` (`:43-45`). The provider string is passed through unmodified.
- Persistence — `cluster/usage.go:107-245` (`UsageRecordFromPayloadWithRuntime`): `provider` (`:140, :155, :213`), `model`, auth index/type, tokens, cost fields are stored verbatim in `usage` (indexes on provider/model/auth `:28, :62-64`). **There is no provider allowlist on the usage path**; the only provider-sensitive logic is a cache-token normalisation heuristic (`usageUsesSeparateCacheBuckets` `:287-305`). So per-credential usage, cost and the `/usage`-family management views work for an unknown provider name as long as the node reports `auth_index` (it is the same value Home handed out in the dispatch reply, `pop/dynamic/dispatch.go:175`).

### Quota view: hard-coded provider allowlist — plugin providers are dropped
- `upsertQuotaFromUsageRecord` (`internal/cluster/quota_ingestion.go:125-173`) → `resolveQuotaUsageCredential` (`:175-197`) returns "not planned" when `!quotaProviderPlanned(provider)` (`:180-182`) or the credential type is not `oauth`/`file_auth` (`quota_snapshots.go:1147-1157`).
- `quotaProviderPlanned` — **`internal/cluster/quota_snapshots.go:1814-1821`: only `claude`, `antigravity`, `codex`, `kimi`, `xai`** (after `normalizeQuotaProviderID` `:1823-1834`, which maps `anthropic→claude`, `grok→xai`). Any plugin provider (e.g. `github-copilot`) is silently excluded from quota snapshots / the quota dashboard.
- Header-derived quota windows exist only for codex (`quota_ingestion.go:28-33, 235-238`). Adding a plugin provider to the quota view = a code change: extend the allowlist (`:1816`) **and** implement a collector/parser for that provider's quota signal (there is no generic one). Not found: any plugin hook for quota collection.

### "Disable when exhausted" / 429 / 401 — provider-agnostic
- `MarkResult` (`internal/cliproxy/auth/result.go:47-…`) keys state by auth ID + canonical model; 429 → per-model cooldown/backoff (`cooldown.go:636-660`), aggregated to a credential-level `Quota.Exceeded` (`result.go:762-789`), reflected in the registry as `SetModelQuotaExceeded`/`SuspendClientModel(reason "quota")` (`manager.go:1015-1093`) which removes the credential from dispatch for that model (`selector.go:342-…`, `manager.go:1441`).
- 401/terminal refresh failure → `disableAuthAfterUnauthorized` sets `Disabled=true, Status=disabled, StatusMessage="unauthorized"` (`result.go:910-940`); disabled auths are skipped everywhere (`manager.go:1026, 1412, 1564, 1685`; `models.go:175`; RESP models `get/models.go:99`).
- The only provider-specific branches in the result path are `antigravity` and `codex` (`result.go:1049, 1077`) — extra parsing, not gating. Nothing here would treat a plugin provider differently.
- The node-side reporting of `plugin-status` is orthogonal and does not affect credential availability.

## Q5. Model naming, pooling, aliases, and the fleet-facing model list

### (a) Client model name → candidate credentials
1. **Registration.** Every credential registers *its own list of model IDs* in the global model registry under its auth ID and a provider key: `registerResolvedModelsForAuth` (`internal/home/models.go:115-124`) → `registry.RegisterClient(clientID, provider, models)` (`internal/registry/model_registry.go:171-…`). The registry keeps, per model ID, a count and a `Providers map[provider]count` (`addModelRegistration` `:381-421`) and, per client, its model list (`clientModels`). Which list a credential registers depends on provider: built-in tables for `gemini/claude/codex/kimi/xai/devin/meta/antigravity…` (`models.go:255-323`), config-declared models for API-key/openai-compat entries (`:335-437`), and **for plugin providers whatever the Home-loaded plugin returns from `ModelsForAuth`** (`:214`, `plugin_runtime.go:165-248`).
2. **Post-processing per credential**, in this order: excluded models (`applyExcludedModels` `models.go:654`), `oauth-model-alias` (`applyOAuthModelAlias` `:926-…`), then `Prefix` (`applyModelPrefixes` `:691-733`: adds `<prefix>/<id>` and keeps the bare id unless `force-model-prefix`).
3. **Dispatch.** `dispatchForAPIKey` (`internal/home/runtime.go:886`) → `dispatchWithOptions` (`:931`): `providers = availableProviderKeys()` (`:947`; `auth_apply.go:186-210` = every distinct provider that has a non-disabled auth) → `coreManager.Dispatch(ctx, providers, reqModel, opts)` (`:965`) → `manager.go:1400-1445`: candidate = every non-disabled auth whose provider is in that list **and** `registry.ClientSupportsModel(auth.ID, routeKey)` (`:1441`; case-insensitive exact ID match `model_registry.go:677-691`), minus API-key restrictions (`allowedModelIDs` `:1331`, `allowedAuthIDs` `:1431`) and per-model cooldown/quota state (`buildDispatchCandidate` `:1443`). A plugin scheduler (if loaded) or the built-in selector picks one (`:1447-1470`; round-robin / fill-first / session-affinity `selector.go:297-340, 440`). Per-credential `resolveDispatchModel` maps the route model to that credential's upstream model (`manager.go:1049`).

### (b) Can one client-facing name be backed by credentials of DIFFERENT providers? **Yes — inherent, and selection happens in Home.**
- Nothing in the candidate loop groups by provider; it filters on `provider ∈ providers` (all of them) and on the model ID. The registry explicitly tracks multiple providers per model ID (`model_registry.go:397-402, 417-420`; `modelRegistrationProviders` `:713-…`).
- So if an Anthropic OAuth credential registers `claude-sonnet-4-5` and a Copilot plugin credential also registers the literal ID `claude-sonnet-4-5`, both are candidates for a request for `claude-sonnet-4-5`, and the built-in selector rotates across them subject to `priority` (`authPriority` `selector.go:154`), cooldown and session affinity. The node receives whichever credential Home picked (`pop/dynamic/dispatch.go:128-202`) and must be able to execute that provider — pooling therefore requires every node to have the plugin loaded.
- **The pool key is the exact model ID string.** If the plugin names models differently (`gpt-4.1`, `copilot/claude-…`, etc.) they do not pool with native names unless an alias makes the IDs coincide (see c). Also note `force-model-prefix` breaks pooling by design (only `<prefix>/<id>` remains, `models.go:727`).
- The "mixed" provider path (`manager.go:1340-1345, plugin_hooks.go:216-219`) is the same mechanism; there is no per-provider dispatch mode.

### (c) Alias / display label while staying in the same pool
Three mechanisms, none of which is a "display label"; all create or rename **model IDs**:
1. **`oauth-model-alias`** (config `internal/config/config.go:173-179, 313-319`; management routes `/oauth-model-alias` `managementhttp/server.go:348-351`): per channel, `{name → alias, fork, force-mapping}`. With `fork: true` the alias is **added** as an extra ID on the same credential (`applyOAuthModelAlias` `models.go:926-…`), so both names route to the same credential, and the alias name pools with any other credential registering the same alias name. Without `fork` it renames. `force-mapping` rewrites the response model field back to the alias (`config.go:546`; dispatch reply `force_mapping`/`original_alias` `pop/dynamic/dispatch.go:161-168`). **Limitation for plugins:** Home's own application is gated by `OAuthModelAliasChannel` (`internal/cliproxy/auth/oauth_model_alias.go:305-327`), which returns `""` for any provider other than `vertex, claude, codex, antigravity, kimi, xai, meta, devin` — so Home does **not** apply `oauth-model-alias` to a plugin provider's models itself (`plugin_runtime.go:240` calls it with the plugin's providerKey → no-op). However the SDK host hands the full alias map (keyed by normalised provider, unfiltered) to every plugin as `HostConfigSummary.OAuthModelAlias` (**SDK** `internal/pluginhost/auth_provider.go:20-64`; `sdk/pluginapi/types.go:196-203`), so a plugin **can** apply `oauth-model-alias.<its-provider>` itself when building `ModelsForAuth`. Whether the community Copilot plugin does is a Task 1 question. If not, making Home apply it generically is a 1-line change at `oauth_model_alias.go:324-325` (`default: return provider`).
2. **Per-credential `Prefix`** (`applyModelPrefixes` `models.go:691-733`): gives `<prefix>/<id>` in addition to `<id>` (pooling on `<id>` preserved) unless `force-model-prefix`.
3. **Model groups / channel groups** (`internal/cluster/model_groups.go`, `channel_groups.go`; routes in `managementhttp/server.go`): these are **API-key access control, not aliasing**. A model group detail binds a `model_id` to channel groups (`model_groups.go:22-26`; `ModelGroupDetailRecord.ModelGroupID` `cluster/models.go:488`), a channel group is a set of `auth_id`s (`channel_groups.go:19-22`), and API keys reference model groups (`cluster/api_keys.go:1136-1151`). At dispatch they become `allowedModelIDs` / `allowedAuthIDs` filters (`manager.go:1331, 1431`) — i.e. they can **narrow** a model's pool to specific credentials for a given API key, but cannot rename a model or give it a label. `grep` for model/channel groups in `internal/home`, `internal/cliproxy`, `internal/respserver` found nothing beyond that filter path; I did not trace end-to-end how `allowedAuthIDs` is populated from the group tables. Group `group_name`/`channel_name` are admin labels only.
**Net:** to expose Copilot's Claude models under the same name as native Anthropic, either (i) the plugin must emit the native IDs, or (ii) use `oauth-model-alias` with `fork: true` (once it applies to the plugin channel) so both credentials register the shared ID.

### (d) How the fleet-facing model list is produced
- Nodes get the model catalogue from Home over RESP: `GET models` (`internal/respserver/get/models.go:15-32`) or the API-key-authenticated `GET <json {"type":"models",…}>` (`get/default.go:51-52, 60-78`). Both call **`buildModelsJSON`** (`get/models.go:36-135`): iterate every non-disabled auth (`:97-101`), compute a **provider bucket key** (`resolveGroupKey` `:41-68`: the provider name, except `codex` is split into `codex-free/plus/team/pro` by `plan_type`), and add `registry.GetModelsForClient(auth.ID)` into that bucket, de-duplicated by ID **within the bucket** (`:75-94, 106-108`). Output is `{ "<provider>": [ModelInfo…], … }` sorted by ID (`:112-134`).
- So it is a **union of all credentials' registered models, grouped by provider**. A model ID backed by two providers appears once under each provider key. A plugin credential's bucket key is its `auth.Provider` (e.g. `github-copilot`). How the node merges these buckets into its `/v1/models` response (and whether it de-duplicates across buckets or applies the API key's model-group filter there) is node code — Task 3.
- Additionally `registry.GetAvailableModelDefinitions` (`model_registry.go:693-711`) returns each model once with a `providers[]` list; used by Home's own management/model endpoints, not by the RESP models path.

## Q6. `X-CPA-SUPPORT-PLUGIN`

- **Home does not compute this header itself.** In this repo the only reference is the CORS `Access-Control-Expose-Headers` list (`internal/managementhttp/server.go:119-131`). Home's own `setBuildInfoHeaders` sets only `X-CPA-HOME-VERSION/COMMIT/BUILD-DATE` (`:721-728`).
- It is set by the **embedded CPA SDK management middleware**, which Home runs on all management routes (`server.go:667, 673` and the no-route fallback `:760-761`): **SDK** `internal/api/handlers/management/handler.go:266-270` → `c.Header("X-CPA-SUPPORT-PLUGIN", pluginhost.SupportPluginHeaderValue())`.
- **Gate = CGO at build time, via Go build tags:** **SDK** `internal/pluginhost/support.go:3-6`; `support_cgo.go:1-5` (`//go:build cgo` → `"1"`); `support_nocgo.go:1-5` (`//go:build !cgo` → `"0"`). The dynamic loader itself is `//go:build cgo && (linux || darwin || freebsd)` (`loader_unix.go:1`) with a stub for `!cgo && !windows` (`loader_unsupported.go:1`). Because Home links the same package, the value reported by Home reflects **Home's own binary** (whether Home can `load-in-home`), not any node's.
- Home's Docker image builds with `CGO_ENABLED=1` (`Dockerfile:19`, glibc/`debian:bookworm` runtime `:21`), so the fleet's `cpa-home` reports `1`. Release workflow: CGO=1 for the linux/darwin matrix (`.github/workflows/release.yaml:222, 325`), CGO=0 for other targets (`:427, :554`). FLEET.md already documents the CGO requirement.
- **What the management panel does with it: not found in this repo.** The panel is not vendored (`internal/managementasset/static/` is a `.gitkeep`; FLEET.md says it is mirrored from the running instance). `docs/management/api.md:68` only says "`1` when the current binary was built with CGO enabled; `0` otherwise. Same semantics as CPA management API." I did not read the panel source, so I cannot say whether it hides the store UI on `0`.

## Practical implications for ws-0002 (Copilot via community plugin)
1. Register the plugin with **zero Go changes**: host a `registry.json` (schema 2, `direct`, artifacts for `linux/amd64` + `darwin/arm64` with sha256) and add it to `plugins.store-sources`; or hand-write the `store` manifest via `PUT /config.yaml`. Set `plugins.enabled: true`.
2. Set `plugins.configs.<id>.load-in-home: true` — required both for `GET /<provider>-auth-url` to exist and for the credential to register any models (otherwise it is unregistered and never dispatched). Home is CGO-built, so this is feasible; the artifact must exist for linux/amd64.
3. Every node must also load the plugin (plugin-sync does this automatically once installed) to execute dispatched requests.
4. Login: device-code works through the generic start/poll contract; expect to need a tiny Home patch to surface `user_code` if the plugin doesn't embed it in the URL.
5. Multiple Copilot accounts = multiple logins, provided the plugin emits distinct `AuthData.ID`s (Task 1 to confirm).
6. Usage/cost accounting works unchanged; the **quota dashboard will not** show Copilot credentials without code (`quota_snapshots.go:1816` + a collector).
7. Pooling with native Anthropic credentials happens automatically if model IDs match; if the plugin's IDs differ, `oauth-model-alias` (`fork: true`) is the tool, but Home only applies it to built-in channels today (1-line change) unless the plugin applies the host-supplied alias map itself.
