### Dedupe work in SQL terms

The schema adds `usage.dedupe_key TEXT NOT NULL DEFAULT ''` and partial unique index `idx_usage_dedupe_key ON usage(dedupe_key) WHERE dedupe_key <> ''`. Each synchronous batch fetches up to500 complete usage JSON payloads:

```sql
SELECT id, payload FROM usage
WHERE id > ? AND dedupe_key = '' ORDER BY id ASC LIMIT 500;
```

The Go code hashes `execution_id` when present; otherwise it sanitizes secrets, removes Home/node runtime fields, canonicalizes JSON, and hashes that payload. It then updates the first occurrence of each key in the batch using a500-row `UNION ALL` value relation:

```sql
UPDATE usage SET dedupe_key = v.usage_key
FROM (SELECT CAST(? AS BIGINT) AS usage_id, CAST(? AS TEXT) AS usage_key
      UNION ALL SELECT CAST(? AS BIGINT), CAST(? AS TEXT) /* up to500 */) AS v
WHERE usage.id = v.usage_id AND usage.dedupe_key = ''
  AND NOT EXISTS (SELECT 1 FROM usage AS keyed
                  WHERE keyed.dedupe_key <> '' AND keyed.dedupe_key = v.usage_key);
```

Cost includes reading every pre-dedupe JSON payload, JSON/hash CPU, updating each unique usage row and maintaining every existing usage index, plus new index creation and WAL/temp growth. Duplicate existing events are neither deleted nor re-billed. R2 marks remaining blank rows in each processed batch as `legacy-duplicate:<row ID>`; this row-specific prefix cannot equal generated `exec:` or `sha256:` event keys, so the unchanged unique index remains valid and redelivery lookups still find only genuine event keys. This deliberately spends one small index entry per historical duplicate rather than adding a tracking table, changing snapshot formats, or maintaining a high-water mark.

Before backfill, both backends idempotently install `CREATE INDEX IF NOT EXISTS idx_usage_dedupe_pending ON usage(id) WHERE dedupe_key = ''`. Warm scans search this sparse index; after completion it is empty. New old-writer blank rows enter it automatically and are still repaired. The cursor is in-memory; cancellation/interrupt resumes from blank rows on next startup. If interrupted between key assignment and duplicate marking, only remaining blanks are rehashed safely. Migration is not background serving work. Generated-fixture tests cover old-schema column/index addition, same/cross-batch duplicates, late old-writer repair, canceled contexts, warm-start zero scans/hashing, and EXPLAIN QUERY PLAN use of the pending index; both SQLite and PostgreSQL exercise duplicate markers. These tests cannot substitute for the large-copy timing.
